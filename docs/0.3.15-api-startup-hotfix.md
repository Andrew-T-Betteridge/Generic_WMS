# DYNETIC WMS 0.3.15 API startup hotfix

0.3.14 migrated the production database correctly but the 0.3.14 API process
failed before listening because Fastify saw two registrations for:

`GET /api/admin/audit`

The older implementation was in `admin-rbac.ts`; the control-plane
implementation was in `admin-operations.ts`.

0.3.15 makes `admin-operations.ts` the canonical owner and moves the prior RBAC
read endpoint to:

`GET /api/admin/legacy-v0313/audit`

The release also permanently strengthens TEST: every TypeScript API source file
is scanned for duplicate static Fastify method+path registrations, then a real
API process must start against `fulfilment_test`, serve `/health` as 0.3.15 TEST,
and enforce authentication on the canonical audit endpoint.

The immutable `dynetic-wms-v0.3.14` tag is not altered.


## V4 semantic-version test correction

The 0.3.15 V1/V2/V3 apply logic replaced `0.3.14` version strings but did not
explicitly update the integer semantic-version assertion in test 015:

`(v_info->>'patch')::INTEGER<>14`

V4 corrects that assertion to patch `15`, verifies that no stale patch-14
assertion remains, and captures the complete canonical TEST child-process stdout
and stderr into permanent repository log files.


## V5 notification route ownership correction

V4's all-TypeScript route scan exposed one remaining duplicate:

`GET /api/admin/notifications`

registered in both `admin-monitoring.ts` and `admin-operations.ts`.

V5 keeps the new control-plane endpoint canonical in `admin-operations.ts` and
moves the older monitoring read implementation to:

`GET /api/admin/legacy-v0313/notifications`

The whole-source static route scan and real Fastify startup check remain in the
canonical TEST gate.


## V6 TEST runtime environment correction

V5 cleared the complete static Fastify route scan: 107 route registrations with
no duplicate method+path pairs.

The real API process then stopped before listening because the startup smoke
launcher did not provide the hardened environment contract. The first explicit
error was:

`ENVIRONMENT_CONFIGURATION_INVALID: DYNETIC_ENVIRONMENT is required`

The environment hardening also requires TEST to use the isolated test database,
the dedicated TEST port and OIDC rather than the DEV_HS256 shortcut.

V6 therefore launches the real API smoke with:

- `DYNETIC_ENVIRONMENT=TEST`
- `DB_NAME=fulfilment_test`
- `PORT=3101`
- `STRIPE_MODE=TEST`
- `AUTH_MODE=OIDC`
- non-secret placeholder Auth0 issuer/audience/JWKS values suitable for startup
  and unauthenticated-route verification

No production credentials are copied into the TEST smoke.


## V7 admin HTTP semantics correction

V6 proved that the real Fastify process now starts under the hardened TEST
environment and reaches the canonical admin route. The remaining failure was
semantic rather than startup-related:

`GET /api/admin/audit` without a bearer token returned HTTP `400`.

The operations module's error mapper checked generic `*_REQUIRED` validation
before authentication and permission errors. Therefore
`AUTHENTICATION_REQUIRED`, `PERMISSION_REQUIRED`, and `ADMIN_REQUIRED` could be
misclassified as client-validation errors.

V7 corrects the mapping order:

- authentication failures -> `401`
- permission / admin-access failures -> `403`
- not-found -> `404`
- ordinary invalid/missing request data -> `400`
- disallowed/conflict operations -> `409`

The runtime TEST smoke now requires exactly HTTP `401` for an unauthenticated
canonical admin endpoint. This matches the admin frontend contract: 401 means
session/sign-in issue; 403 means an authenticated principal lacks permission.


## V8 resilient sendError patch

V7 failed safely before validation because its apply step expected one exact
multi-line text representation of the `sendError` helper. The current source
still had the known pre-fix semantics, but formatting/line-ending drift meant
the exact block comparison did not match.

V8 keeps the intended HTTP-semantics fix unchanged, but locates the helper
structurally: exactly one `sendError(...)` immediately before `lim(...)` must be
present. That single helper is replaced, then the mapping order is verified
before validation is allowed to continue.

The runtime smoke remains strict and requires exactly HTTP 401 for an
unauthenticated canonical admin endpoint.


## V9 quoted child-process argument transport

V8 cleared the complete strict TEST gate, including the real Fastify startup and
exact unauthenticated HTTP 401 check. It then recreated and freshly bootstrapped
the independent verification database successfully.

The remaining V8 failure was exclusively in the validation harness. The
`Verify-FreshBootstrap.ps1` child process received:

`C:\Program Files\PostgreSQL\18\bin\psql.exe`

through `Start-Process -ArgumentList` without preserved quoting. Windows
PowerShell therefore split the value at the space and attempted to execute
`C:\Program`.

V9 builds one explicitly quoted child command-line string before Start-Process,
so path-valued arguments remain intact. The release/product source fix itself is
unchanged.


## V10 release-finisher hardening

V9 validation passed every release gate, including deployment safety. The V9
release wrapper then reached its unrelated-work parking step and its transcript
stopped there.

The product candidate did not fail. V10 hardens the release wrapper itself:

- every mutating native Git operation runs with non-terminating stderr handling
  and is judged by its exit code;
- an active V9/V10 runner or Git index lock causes a fail-closed stop;
- an existing V9 safety stash is detected and restored after the release;
- partially completed commit/tag state is inspected rather than blindly repeated;
- the immutable 0.3.15 tag is never moved;
- the full green validation is repeated before staging;
- unrelated local work is parked with `--keep-index --include-untracked` and
  restored afterwards.

No product/database behavior is changed by V10.


## V11 clean-worktree release finisher

V10 validation passed completely. V10 then stopped after staging and staged-diff
verification, before any commit/tag/deploy step.

V11 intentionally makes no product-source changes and does not rerun the
expensive product validation. It requires the latest V10 validation report to
contain the green PASS marker, re-verifies the release index, commits only the
explicit staged release whitelist, and leaves unrelated local files untouched.

Because release tagging/safety requires a clean tracked tree, V11 creates a
temporary detached clean Git worktree at the release commit. The immutable tag
and deployment-safety verifier run there. This removes the need to stash the
developer's unrelated local work at all.
